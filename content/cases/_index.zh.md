下云不是非黑即白的宗教信仰，而是一场严肃的工程权衡与财务抉择。

在当下的技术舆论中，下云常被简化成两种极端叙事：一种是「人人自建、怒省数百万」的降本神话，另一种是「自建必翻车、人力成本高上天」的恐吓营销。真实的工程世界从非如此极端。

**下云案例库**为成功、部分完成、放弃和回迁提供同一复核模板。目前尚未发布完成评估的案例；文章归档保留来源评论，供后续核对。

## 六个必答问题 {#six}

任何有参考价值的下云复盘，都必须如实回答这六个维度：

| 维度 | 复盘焦点 | 关注的工程事实 |
| :--- | :--- | :--- |
| **1. 搬了什么？** | 迁移范围 | 数据库、文件存储、核心应用还是控制面？哪些模块率先解耦？ |
| **2. 留了什么？** | 战略留存 | 哪些云上能力（如边缘 CDN、全球 Anycast DNS）被刻意保留？ |
| **3. 花了多少？** | 全生命周期成本 | 硬件采购、IDC 机柜、机房跳线、团队工时与过渡期双轨运行费用。 |
| **4. 用了多久？** | 真实时间线 | 从立项决策、架构验证、灰度切流到收敛稳定，实际多久收回成本？ |
| **5. 哪里踩坑？** | 失败与意外 | 遭遇了哪些硬件故障、网络瓶颈或组织阻力？哪些预期被证伪？ |
| **6. 重来怎么做？** | 一线复盘反思 | 以当事工程团队的第一手总结为准，不替他人脑补推论。 |

## 证据标签与校准候选 {#labels}

每个案例都严格打上信源等级标签：**当事团队一手报告**、**公开财报审计**、**行业模型推算** 或 **架构编辑推断**。模型预估绝不能混充为财务审计，所有数字必须与其适用边界一同呈现。

首批校准候选包括 37signals、Ahrefs、探探，以及有公开记录的部分退出或回迁实践。来源、成本口径和时间线核对完成后，才会作为正式案例发布。当事方报告的节省与假设云账单将分别标注。
