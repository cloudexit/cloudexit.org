## 评估单位 {#unit}

评估单位是 **厂商 + 产品 + 地域 + 商业套餐 + 复核日期**。
除非范围内所有重要产品与地域都完成测试，否则不得把结果扩大成公司级结论。
同一家厂商的不同地域、存储类别或合同类型可以得到不同结果。

## 结果状态 {#states}

| 状态 | 含义 |
| --- | --- |
| 通过 | 证据在声明范围内满足该判据。 |
| 部分通过 | 存在实际可用路径，但仍有重要限制。 |
| 未通过 | 证据表明该判据不成立。 |
| 未知 | 证据缺失、不可访问、互相矛盾，或尚未实测。 |
| 过期 | 复核时间已经超过有效窗口。 |

未知不等于失败；过期也不能悄悄继续显示成上一次结果。

## 证据层级 {#evidence}

1. 合同、官方价目表、技术文档、事故报告或厂商机器可读数据。
2. 带输入、日期、地域、账号类型和原始输出的可复现实测。
3. 具名组织、明确工作负载的一手运营记录。
4. 带一手证据链接的独立报道。
5. 明确标注的编辑分析，且不能单独支撑评级。

每条引用都必须记录采集日期。截图可以保存短暂存在的价格或政策状态，
但在有稳定网址时不能用截图代替原始链接。

## 复核流程 {#flow}

1. **划定范围**：明确产品、地域、套餐与被测功能。
2. **采集证据**：优先收集一手来源并保存来源窗口。
3. **执行复现**：在权限允许时实测导出、接口或价格。
4. **逐项评审**：填写 C1–C5，并保留分歧与未知项。
5. **事实通知**：能找到联系人时，把事实草稿发给厂商或维护者核对。
6. **同步发布**：结果、证据包、复核日期与失效日期一起发布。
7. **按期回看**：出现重大变化或进入复核窗口时重新检查。

数据集目标按季度发布；单条评级如果 180 天没有重新核查，就自动过期。
这样即使季度更新延误，也不会把旧信息伪装成当前状态。

## 纠错与申诉 {#appeals}

任何人都可以提交反证。有效申诉需要指出具体字段、适用范围、日期，
并给出一手来源或可复现实测。事实错误应及时纠正并保留修订说明；
方法争议进入下一个标准版本讨论，不能看到结果后再倒改旧判据。

## 利益冲突 {#conflicts}

发起人冯若航为自托管 PostgreSQL 平台 Pigsty 提供商业支持，
组织选择自建数据库时，他可能从中受益。任何点名商业工具的页面都必须重复相关披露。
评审者还需记录任职、投资、赞助、咨询与竞争关系。
披露不能证明结论正确，它只是让读者在检查证据时一并评估偏差风险。

## 版本规则 {#versioning}

- 标准按语义化文档版本管理：不兼容判据升主版本，新增字段或阈值升次版本，澄清升补丁版本。
- 数据集以日期加修订号发布，不覆盖旧快照。
- 厂商结果必须指向使用的准确标准版本与数据版本。
- 名录保留过期与撤回状态，不用删除来抹掉历史。
