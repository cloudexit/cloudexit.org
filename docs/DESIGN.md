# cloudexit.org 设计大纲

状态：**v0.1 骨架**  
主题：Oink 1.0.0（Hugo Module）\
语言：English 默认 + 简体中文  
部署形态：静态站点；本阶段只交付本地骨架，不声称已经部署

## 1. 单一职责

把「下云」从一个人的观点，变成一套可验证的公共标准和一份可查证、可复算、可纠错的证据。

| | vonng.com/cloud | cloudexit.org |
| --- | --- | --- |
| 体裁 | 署名评论、编年文章 | 标准、数据集、清单、档案、手册 |
| 人称 | 作者认为 | 按某条判据，证据支持/不支持什么 |
| 默认语言 | 中文 | 英文，核心标准中文对照 |
| 更新方式 | 事件驱动 | 版本与复核周期驱动 |
| 可引用性 | 引用作者 | 引用方法、数据版本与具体记录 |
| 厂商传播动机 | 很弱 | 通过可审计标准后，有动机链接结果 |

去人格化不是假装没有立场，而是把结论拆成别人能够复验、反驳和纠错的单元。

## 2. 价值主张

英文首屏：

> Cloud exit is a capability, not an event.

中文首屏：

> 上云是选择，下云是能力。

全站统一界定：

> 卖资源是买卖；为「你走不了」定价才是收租。

这一定义带来三个约束：

1. 不要求所有人离开云，只要求组织能够衡量自己是否有离开的能力。
2. 不按厂商身份划敌我，只检查退出收费、导出、接口、承诺和故障问责行为。
3. 云、CDN、IDC、托管服务与硬件厂商都可能成为下云能力的组成部分。

## 3. 目标读者与入口

| 读者 | 首要问题 | 最短入口 | 深入路径 |
| --- | --- | --- | --- |
| CTO / 架构负责人 | 我们是否被锁定？ | 5 分钟 C1–C5 自查 | 标准 → 名录 → 手册 |
| CFO / FinOps | 溢价和退出成本是多少？ | 30 分钟成本模型 | 账本 → 数据 → 案例 |
| SRE / DBA / 平台团队 | 真要走时怎么做？ | 一个下午下云演练 | 手册 → 档案 → 案例 |
| 采购 / 法务 | 哪些条款制造锁定？ | C1、C4、C5 | 标准 → 谈判手册 |
| 厂商 / 服务商 | 如何证明自己可退出？ | 方法与数据契约 | 评级 → 申诉 → 徽章 |
| 研究者 / 媒体 | 哪些结论可引用？ | 数据目录与来源账 | 账本 → 档案 → 修订记录 |

## 4. 五个板块是一条论证链

```text
01 标准：谁在收租？
   ↓ 那我交了多少？
02 账本：租金是多少？
   ↓ 贵之外还有什么风险？
03 档案：风险发生过什么？
   ↓ 有人真的走出去过吗？
04 案例：谁做成、谁失败、为什么？
   ↓ 我下周一做什么？
05 手册：从一次演练开始。
```

首页的 capabilities 分区就是这条链。编号 01–05 表示阅读顺序，而不是装饰。

## 5. 信息架构

### 5.1 `/standard/` 标准：发牌之前先定义牌

支撑结论：敌我按行为划，而且任何人都能复验。

| 页面 | 职责 | 发布条件 |
| --- | --- | --- |
| `/standard/` | 五条判据总表；说明这份标准不是什么 | v0.1 已具备 |
| `/standard/c1-no-exit-toll/` | 出网、取回、提取是否构成退出罚金 | 定义、验证、算例、边界齐全 |
| `/standard/c2-whole-data-export/` | 数据与必要元数据能否整体恢复 | 同上 |
| `/standard/c3-standard-interfaces/` | 核心操作能否通过公开接口重建 | 同上 |
| `/standard/c4-no-commitment-lock/` | 承诺、额度与合同是否搁浅价值 | 同上 |
| `/standard/c5-accountable-downtime/` | 故障、补救与责任是否可审计 | 同上 |
| `/standard/method/` | 评估单位、证据层级、状态、复核、失效、申诉 | v0.1 已具备 |
| `/standard/registry/` | 从结构化 YAML 生成的厂商/产品名录 | 首条完整证据包通过复核 |
| `/standard/badge/` | 徽章、嵌入代码与使用条款 | 方法经真实样本校准后 |
| `/standard/scope/` | 射程内、射程外、潜在盟友 | v0.1 已具备 |

每条判据必须保留“边界与反驳”。它不是礼貌附录，而是可信度的主要来源。

评级单位固定为：**厂商 + 产品 + 地域 + 套餐 + 复核日期**。不得从一个产品推断整家公司。

### 5.2 `/ledger/` 账本：把形容词变成算术

支撑结论：溢价、退出成本与盈亏平衡点可以复算，但结论取决于工作负载与假设。

| 页面 | 核心变量 | 首批资产 |
| --- | --- | --- |
| `/ledger/model/` | 周期、资金、税、残值、风险、现金/经济成本 | build-vs-buy assumptions |
| `/ledger/compute/` | vCPU/物理核、内存、利用率、冗余、承诺 | EC2/ECS + DHH/探探样本 |
| `/ledger/block-storage/` | GiB、IOPS、吞吐、快照、副本、跨区 | block storage rates/scenarios |
| `/ledger/object-storage/` | 逻辑/物理容量、请求、取回、拓扑、出网 | object scale/breakpoint curves |
| `/ledger/egress/` | 路径、方向、流量曲线、阶梯、端口利用率 | traffic rates + transit curve |
| `/ledger/managed-markup/` | 资源、运维职责、功能使用、限制、风险 | RDS ratios/curves |
| `/ledger/data/` | 版本、来源窗口、状态、许可、校验和 | 三套 2026 研究资产 |

硬规则：每个数字必须带来源、采集日期、产品、地域、币种、单位、期限、公式版本与适用边界。
过期值标注过期并保留，不用新值覆盖历史。

账本默认同时输出：

- 月度和累计成本曲线；
- 规模与时间两个盈亏平衡点；
- 利用率、硬件寿命、人力、电力、资金与增长敏感性；
- 现金成本、经济成本、退出成本；
- 明确列出的未计入项。

### 5.3 `/evidence/` 档案：先有记录，再谈预测

支撑结论：集中度风险、锁定手法与问责缺失已有可观察记录。

| 集合 | 记录结构 | 价值 |
| --- | --- | --- |
| `/evidence/outages/` | 发生/结束、影响、依赖链、时间线、RCA、SLA、整改、置信度 | SEO、媒体引用、C5 证据 |
| `/evidence/lock-in/` | 机制、层次、症状、退出测试、绕行方式、适用范围 | C1–C4 证据与手册输入 |
| `/evidence/claims/` | 准确说法、时间、范围、验证、证据、状态、厂商回应 | 对称核查公开表述 |

档案必须区分：发生日期/发布日期、观察/推断、一手/二手、已知/未知、原始记录/后续修订。

### 5.4 `/cases/` 案例：让适用条件和失败同样可见

支撑结论：下云可以走通，但不是所有情景都适用。

每个案例统一回答六问：

1. 搬了什么？
2. 留了什么？
3. 花了多少？
4. 用了多久？
5. 哪里失败、回退或放弃？
6. 重来一次会怎么做？

案例使用四种证据标签：当事方报告、模型估算、已验证材料、编辑推断。
模型节省不能写成审计节省。成功、部分、放弃、回迁使用同样版面。

### 5.5 `/playbook/` 手册：把立场变成下一步

支撑结论：下云是可以分段、测量、回退的工程能力。

| 页面 | 动作 | 产物 |
| --- | --- | --- |
| `/playbook/exit-drill/` | 在别处恢复一份关键数据并计时 | 下云能力基线 |
| `/playbook/data-first/` | 先建立独立保管、导出、验证、恢复 | 数据主权基线 |
| `/playbook/inventory/` | 盘点数据、接口、身份、控制面、合同与人 | 依赖地图 |
| `/playbook/staging/` | 离线、回放、影子、部分流量、切换、回退 | 分阶段迁移门槛 |
| `/playbook/negotiation/` | 用真实替代方案改善合同 | 自动适用的退出条款 |

全站唯一行动号召是“做一次下云演练”。它即使在最终选择留下时也有价值。

## 6. 首页结构

首页数据位于 `data/home/{en,zh}.yaml`，两种语言保持相同分区与键结构。

1. **Hero**：一句价值主张；CTA 为读判据、查名录；主动说明暂无评级。
2. **Capabilities**：01–05 论证链，每段给问题、方法、价值与视觉摘要。
3. **Criteria cards**：C1–C5 与名录入口，三列。
4. **Scope logo wall**：射程内/潜在盟友，统战声明不藏在内页。
5. **Three actions**：查厂商（5 分钟）、算账单（30 分钟）、做演练（一个下午）。
6. **FAQ**：反云、是否人人要走、证据、申诉、利益冲突。
7. **CTA**：去做一次下云演练。

时间成本排序是转化设计：先让读者完成一个小动作，再进入长文。

## 8. 视觉与交互方向

- 气质：公共标准、工程手册、审计底稿；避免“反云檄文”或 SaaS 营销页风格。
- 基色：深蓝表示方法与可信度；铜色表示需要注意的成本与摩擦；五个板块各有克制的语义色。
- 字体：Oink `technical`；数字、公式、版本和状态优先对齐与可扫描。
- 首页：使用 Oink 的网格、规则线和技术面板，不依赖 Hero 图片也能成立。
- 图表：同一图中必须显示单位、零点、来源窗口和适用范围；不得只给视觉结论。
- 状态：Pass/Partial/Fail/Unknown/Stale 使用文字加颜色，不只靠颜色表达。
- 移动端：卡片单列、表格可横向滚动、CTA 仍保留明确时间成本。
- 无障碍：键盘可达、焦点可见、标题层级正确、图表有数据表或文本等价物。

Hero 与社交分享图在视觉身份确认后再补；v0.1 不用占位 AI 图掩盖未完成品牌工作。

## 9. 双语策略

- 英文是跨组织引用与厂商参与的默认语言。
- 标准、方法、名录、射程和核心演练保持完整双语。
- 账本、档案和案例允许先发英文全文 + 中文摘要，但页面必须明确翻译状态。
- 中文旧文作为来源回链，不整篇复制成英文站内容。
- 路由与锚点在两种语言间保持对应，首页键结构由检查脚本校验。

## 10. 数据与治理

公开数据集必须包含：

- 不可变版本号、发布日期和来源窗口；
- 机器可读 schema 与数据字典；
- 来源账、采集日期、许可/复用说明；
- 生成脚本或明确计算公式；
- 校验和与验证结果；
- 过期、撤回和更正机制。

厂商评级以 180 天为有效期，数据集目标按季度发布。过期展示为 Stale，不自动沿用旧结论。

## 11. 利益冲突与参与机制

发起人冯若航为自托管 PostgreSQL 平台 Pigsty 提供商业支持，可能从自建决策中受益。
首页、方法页以及点名商业工具的页面都要披露相关关系。

可信度来自可检查过程，不来自“中立”自称：

- 一手来源优先；
- 公式与原始数字可复算；
- 未知与反例不隐藏；
- 厂商可提交反证；
- 事实纠错保留修订；
- 方法争议进入新版本，不倒改旧判据。

## 12. SEO 与可引用性

- 每个故障、判据、案例和数据版本有稳定永久链接。
- 标题优先使用问题和对象，不使用只有当时热点才能理解的梗。
- 每页提供 Markdown 输出；首页和各节提供 LLMS/NAVJSON/LLMSFULL。
- 结构化记录保留原始来源、发生日期、发布日期与更新时间。
- 旧文章回链到对应标准/账本/档案记录；本站回链原始中文文章。
- 后续为 Dataset、Article、FAQ 和可验证 Organization 记录添加结构化数据。

## 13. 分期

### P0：可引用的最小站点

- 首页；
- 五条判据、方法、射程；
- 故障档案结构与首批经过复核的记录；
- 下云演练；
- 利益冲突与编辑规范。

上线门槛不是“页面够多”，而是至少有一类资产值得外部引用。

### P1：第一次公共承诺

- 10–15 个产品级真实评级；
- 每条评级证据包、复核日期与失效日期齐全；
- 厂商事实通知与申诉流程跑通；
- 演练表格可下载。

没有真实来源时宁可保持空名录。

### P2：数据与案例

- 计算、RDS、块存储、对象存储、出网模型；
- CSV/YAML 数据版本与来源账；
- DHH、探探、Ahrefs 等首批案例；
- 至少一个失败或放弃案例。

### P3：生态化

- 徽章与嵌入代码；
- 外部贡献与复核者机制；
- 独立资助/赞助披露；
- 历史版本浏览与数据 API。

## 14. 三个真实风险

1. **利益冲突。** 隐藏比承认更伤可信度；用完整披露、公开方法与可复算数据处理。
2. **名录是长期负债。** 发布评级就是承诺维护；用失效日期和显式 Stale 防止陈旧信息伪装成当前结论。
3. **双语维护成本。** 核心标准全量双语，长篇证据允许英文正文 + 中文摘要，并通过检查维持结构对齐。

## 15. 发布门槛

以下状态必须分开报告：

1. 本地源文件完成；
2. 严格 Hugo 构建通过；
3. 英中真实路由与移动端人工检查；
4. 数据来源与过期状态审计；
5. Git 提交与远端推送；
6. CI 构建；
7. 托管平台部署；
8. cloudexit.org DNS/TLS；
9. 公网 EN/ZH 渲染与下载校验。

本阶段只覆盖 1–2；不得把本地骨架描述成已经发布。
